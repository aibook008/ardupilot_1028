## 1. 概念确认（可以按这个钉死）

### 1.1 我们真正在交付什么

```
硬件（买） ──► 只提供算力、接口、传感器外壳
                │
软件（做） ──► 飞控机载软件 + 地面站 + 适配/联调胶水
                │
仿真（做） ──► 在上天前把软件逻辑与接口风险打穿
                │
通信与关联系统联调（做）──► 把“能跑的软件”变成“能飞的系统”
```

| 层次 | 性质 | 我们的工作量 |
|------|------|--------------|
| 飞控板 / 天线 / 数传 / 遥控 / RID 模块 | **采购 + Bring-up** | 小（选型已覆盖） |
| 机载控制软件（模态/过渡/保护/估计/混控） | **核心自研/定制** | 大 |
| 通信协议与链路（机载↔地面、机载↔航电） | **核心集成** | 大 |
| 关联系统联调（动力/舵机/倾转/传感/GCS/仿真） | **关键路径** | 大 |
| SITL / 联合仿真 / HIL | **风险收敛手段** | 大，且前置 |

**结论**：一期文档把需求/架构/控制律/仿真计划立住之后，从二期起主战场就是 **软件实现 → 仿真验证 → 通信与关联系统联调** 的循环，不是继续堆硬件设计。

### 1.2 “通信与关联系统联调”指什么（工作拆开）

不要把它理解成“调一下数传”，而是四条联调链：

| 联调链 | 两端 | 主要内容 | 失败表现 |
|--------|------|----------|----------|
| **A. 航电总线链** | 飞控 ↔ 电调/舵机/倾转/CAN 外设 | 节点、指令、反馈、时序、失效帧 | 电机不动/方向反/倾转不同步 |
| **B. 传感链** | 飞控 ↔ IMU/GPS/空速/电流 | 驱动、校准、健康、余度切换 | 估计漂、无法解锁、误保护 |
| **C. 测控链** | 飞控 ↔ 数传/遥控 ↔ 地面站 | 协议、带宽、失控、任务/参数/日志 | 看不见飞机、丢控、任务传不全 |
| **D. 仿真链** | 飞控软件 ↔ SITL/MATLAB/HIL | 作动/传感交换、时钟、故障注入 | “仿真能飞、真机不能”或相反 |

另外两条按阶段插入：

| 联调链 | 两端 | 阶段 |
|--------|------|------|
| **E. 合规链** | 飞控 ↔ Remote ID ↔（网络）平台 | W8 硬件联调，W12 报送 |
| **F. 机体链** | 飞控 ↔ 全机电源/线束/机构 | W6 缩比，W9 验证机 |

**软件里的“通信”**：协议栈 + 消息语义 + 频率/优先级 + 失效处置，写在机载软件与地面站里。  
**“关联系统联调”**：用真实或半真实对象把 A–F 链逐条打通，并回归到仿真用例。

### 1.3 正确工作闭环（二期起每周都按这个转）

```
改软件（控制/保护/协议）
    → SITL 逻辑回归（含故障注入）
        → 关联系统联调（先台架/HIL，再上机）
            → 日志归零 → 再改软件
```

没有“先写完美软件再联调”；也没有“先联调再补仿真”。  
**仿真保逻辑与安全网，联调保接口与真实时序，二者夹击软件。**

## 2. 接下来的重点工作（按优先级）

> 排序原则：卡首飞与卡交付的先做；硬件采购并行但不占主精力。

### P0 — 立刻开干（本周～W3）

| # | 工作 | 为何关键 | 出口 |
|---|------|----------|------|
| 1 | **机载软件基线可编译运行**（目标板 + SITL） | 没有可跑二进制，后面全空 | `plane` SITL 日构建 |
| 2 | **倾转过渡 + ABORT 状态机落地** | 协议硬缺口，也是最高技术风险 | SITL：SIM-TR-01/02/04 通过 |
| 3 | **测控链冒烟**（飞控↔GCS：心跳/参数/模式/解锁） | 没有测控就无法调参与试飞 | 链路上行指令、下行遥测稳定 |
| 4 | **仿真环境 L1**（倾转 frame + 默认参数包） | 控制律迭代唯一快速试验场 | 一键复现悬停→转换场景 |

### P1 — W4–W6（二期主战场）

| # | 工作 | 归属 | 出口 |
|---|------|------|------|
| 5 | 旋翼串级 + 固定翼 L1/TECS 参数在 SITL 跑通 | 软件+仿真 | SIM-MC/FW 关键用例 |
| 6 | 倾转补偿 / 混控 / 通道映射与 **航电总线链** 台架联调 | 软件+联调 A | 舵面/电机方向正确 |

| 10 | 缩比机联调与试飞支撑（参数包、检查单、日志流程） | 联调 F | 缩比科目闭环 |

| # | 工作 | 说明 |
|---|------|------|

### 不该再当成主线的

- 再写厚硬件原理图/自研板卡（除非供应商产品不满足且已证实）  
- 一期七份文档从零重写（应在现稿上改）  
- 过早铺板级三余度（合同未强制前，只留接口）

## 3. 文档哪些值得继续迭代

### 3.1 总原则

| 类型 | 策略 |
|------|------|
| **活文档（随软件/联调变）** | 高价值，持续改 |
| **基线文档（评审后冻结，仅变更控制）** | 中价值，少改 |
| **一次性/阶段性清单** | 低迭代价值，用完归档 |
| **内部通读/实现笔记** | 对开发高价值，不对甲方也能迭代 |

### 3.2 一期已出品：迭代价值排序

| 优先级 | 文档 | 为何继续迭代 | 怎么迭代 |
|--------|------|--------------|----------|
| **★★★★★** | `06 控制律设计报告` | 软件实现的唯一设计真源；ABORT/补偿/参数都会变 | 每完成一块控制功能就改一节；试飞后升 V1.0 锁增益 |
| **★★★★★** | `07 仿真测试计划` → 将来的《仿真测试报告》 | 用例即验收网；联调发现的洞要补进用例 | 计划改用例表；执行后出报告，不要另起炉灶 |
| **★★★★☆** | `04 ICD` | 通信与关联系统联调的合同级依据；针脚/消息/通道会在 Bring-up 时钉死 | V0.9→V1.0（板型到货后）；CAN/RID 消息表二期追加 |
| **★★★★☆** | `01 SRS` | 需求跟踪矩阵要跟着实现/测试状态更新 | 少改需求条文；多维护 §7 状态列与开放问题关闭 |
| **★★★☆☆** | `02 SDD` | 模块落地后补接口细节、RID/保护挂载点 | 大结构不推翻；加“实现备注/模块责任人” |
| **★★★☆☆** | `05 特性分析` | **仅当气动/惯量数据到达或试飞揭示新危险区时**大改 | 数据到 → V1.0；否则别空转润色 |
| **★★☆☆☆** | `03 选型报告` | PO 下达、到货验收后基本冻结 | 只补到货偏差与备选启用记录 |
| **★★☆☆☆** | `08 PHA/FMEA` | 仿真/试飞后更新 RPN，不是每周改 | 二期报告后 V1.0；首飞后 V1.1 |
| **★☆☆☆☆** | `09 W1W2 清单` | 阶段闸门，过了就归档 | 不再迭代正文 |
| **★☆☆☆☆** | `00 索引` | 偶尔改目录 | 有新活文档再更新 |

### 3.3 更值得长期迭代的“内部实现文档”（比一期套话更管用）

这些已在 `docs/`，对**软件与仿真主战场**意义更大，建议作为实现期活文档：

| 文档 | 继续迭代的意义 |
|------|----------------|

| `code_walkthrough_*.md`（quadplane/failsafe/servo/ekf…） | 联调卡壳时的导航图；发现错行号就修 |

甲方交付件 = 从上述活文档**提炼/脱敏**升版；不要维护两套互不相同的技术事实。

### 3.4 推荐的文档节奏（省事且不丢追溯）

```
实现/联调有结论
    → 先改内部通读或控制律/ICD/仿真用例（真源）
        → 里程碑前再刷一版对外 V0.x/V1.0（提炼）
```

**不要**：每周重写七份对外大文档。  
**要**：每周更新控制律参数表、仿真用例结果、ICD 消息/通道、问题单。

## 4. 一句话对齐

- **概念**：硬件采购；软件是产品；仿真是验证器；**通信 + 关联系统联调是把软件变成可飞系统的关键路径**——这个概念正确，按此排期。  
- **接下来**：P0 抓住 **SITL 基线、过渡+ABORT、测控冒烟**；P1 铺开 **控制律闭环 + 航电/传感/HIL 联调 + 保护注入**。  
- **文档**：优先滚动 **控制律、仿真计划/报告、ICD、SRS 跟踪**；选型/W1W2 清单冻结；内部架构与仿真/CAN/日志文档才是日常迭代主阵地。
